# گزارش بررسی نسخه ۰.۲.۳

تاریخ آخرین بررسی: ۲۰۲۶-۱۰-۱۲. بررسی روی کد موجود و فایل عمومی وب‌کلاینت روبیکا
انجام شد؛ هیچ اطلاعات ورود مرورگر به پکیج منتقل نشده است.

| یافته | تغییر |
| --- | --- |
| کاتالوگ بسته خالی بود و ورود زنده فعال نبود | ۲۰۵ نام پروتکل و ۶ alias از فایل عمومی وب اضافه شد |
| transport عمومی با پروتکل Rubika متفاوت بود | آداپتور native شامل AES، امضای نسخه ۶، OTP، کشف DC و WebSocket اضافه شد |
| انقضای سشن فقط پردازش را متوقف می‌کرد | ورود مجدد ترمینالی با یک قفل مشترک برای HTTP، گیرنده و صف اضافه شد |
| ثبت هندلر قبل از ورود خطا داشت | هندلر پیش از سشن قابل ثبت است و هنگام ورود مجدد باقی می‌ماند |
| چند prompt می‌توانستند هم‌زمان باز شوند | ورود ترمینالی چند سشن در همان پردازش سریالی شد |
| ورود حساب دیگر می‌توانست صف قبلی را دوباره استفاده کند | شناسه حساب هنگام تعویض سشن بررسی می‌شود |
| repr مدل، auth را نشان می‌داد | auth و private_key در repr مخفی شدند |
| عملیات sending پس از crash باقی می‌ماند | هنگام بازکردن مجدد، unknown می‌شود؛ بازپخش خودکار انجام نمی‌شود |
| خطای اتصال بعد از ارسال می‌توانست retry شود | نتیجه تأییدنشده به AmbiguousDeliveryError تبدیل می‌شود |
| CLI و دسترسی هم‌زمان به کاتالوگ وجود نداشت | دستور login و methods و with Client و API هم‌زمان اضافه شدند |
| ساخت wheel می‌توانست فایل‌های Python را به‌خاطر include محدود حذف کند | بسته‌بندی اصلاح و محتوای wheel بررسی شد |
| کپی‌کردن `#c=GUID` یا URL وب به‌عنوان `chat_id` باعث رد درخواست می‌شد | ورودی GUID، hash وب و URL وب به GUID خام نرمال می‌شود |
| VS Code از Python سراسری استفاده می‌کرد و import را پیدا نمی‌کرد | برای پروژهٔ نمونه مفسر `venv\\Scripts\\python.exe` در workspace ثبت شد |
| بستن کلاینت وسط ارسال، عملیات نامطمئن را دوباره صف می‌کرد | در نبود تضمین idempotency، وضعیت unknown ذخیره می‌شود و پس از بازگشایی بازپخش نمی‌شود |
| پاسخ خراب، فریم رمزگذاری نامعتبر یا نبود شناسهٔ پیام باعث تکرار ارسال می‌شد | نتیجهٔ تأییدنشده به AmbiguousDeliveryError تبدیل می‌شود؛ خطای اتصال پیش از ارسال همچنان قابل retry است |
| پاسخ HTTP 5xx می‌توانست شکست قطعی گزارش شود | نتیجهٔ ارسال نامطمئن ثبت می‌شود، چون انجام عملیات از این پاسخ قابل اثبات نیست |
| خطای ورود مجدد پشت INVALID_AUTH پنهان می‌شد و چند درخواست دوباره ورود می‌خواستند | SessionRenewalError با علت امن و انگلیسی اضافه شد؛ ورود شکست‌خورده یا رد سشن جایگزین تلاش نامحدود ایجاد نمی‌کند |
| در فراخوانی مستقیم SyncClient، wait و timeout وارد payload می‌شدند | گزینه‌های انتظار به API منتقل می‌شوند و به سرور فرستاده نمی‌شوند |
| شکست یک عضو SessionPool می‌توانست راه‌اندازی سایر اعضا را باز بگذارد | وظایف راه‌اندازی پیش از بستن سشن‌ها لغو و جمع‌آوری می‌شوند |
| آپلود با پاسخ خراب یا بدون access_hash_rec می‌توانست موفق گزارش شود | نتیجهٔ تأییدنشده گزارش می‌شود؛ پاسخ معتبر و هش نهایی برای موفقیت لازم است |

اعتبارسنجی محلی شامل ورود رمزگذاری‌شده با سرور mock، RSA-OAEP، امضای SHA-256،
بردار AES مستقل از Node، handshake WebSocket محلی، فریم‌های batch، خطای
دسترسی در برابر انقضای احراز هویت، ورود هم‌زمان، هندلر پیش از ورود، رمز
دومرحله‌ای، OTP نامعتبر، جلوگیری از تعویض حساب و بازیابی وضعیت پس از crash است.
در بازبینی ۲۰۲۶-۱۰-۱۲، نسخهٔ اولیهٔ موجود ۳۹ تست موفق داشت. تست‌های جدید
پیش از اصلاح، ۱۰ شکست را در مسیرهای بستن برنامه، پاسخ خراب و کلاینت هم‌زمان
بازتولید کردند. مجموعهٔ نهایی شامل ۶۰ تست روی Python 3.14 است؛ سناریوهای
جدید با HTTP mock، ورودی ترمینالی ساختگی و WebSocket محلی اجرا می‌شوند.
محتوای wheel نیز با فایل‌های پروژه تطبیق داده می‌شود.

درخواست عمومی getDCs نیز روی سرویس واقعی موفق شد و سه API و سه WebSocket
برگرداند. لاگ ارسالی کاربر ساخت موفق سشن و خطای INVALID_AUTH هنگام ارسال را
نشان می‌دهد. ارسال و دریافت واقعی، تمام پارامترها و رفتار سرور همه متدها
هنوز تأیید نشده‌اند. کاربر تست حساب واقعی را در ترمینال خود انجام می‌دهد.
نام‌های استخراج‌شده پوشش فایل عمومی وب هستند؛ این گزارش ادعای پوشش
همه APIهای خصوصی روبیکا را ندارد.

resume token در پروتکل وب مشاهده نشد؛ backfill خودکار رویدادهای زمان قطع
پیاده نشده است. APIهای update برای استفاده برنامه موجودند. اجرای رسانه‌ای
WebRTC پیاده نشده است. تضمین deduplication سرویس تأیید نشده و عملیات مبهم
به unknown تبدیل می‌شوند. هر فایل سشن باید در اختیار یک پردازش باشد.
